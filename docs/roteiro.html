Fluxo de uma requisição
⏱ 60 segundos 🎯 Mostrar como funciona na prática

Slide 12
models.py — as 5 tabelas
⏱ 70 segundos 🎯 Explicar o banco em Python
Aqui está o coração do banco. O models.py define cinco tabelas: Funcionário, Cliente, Veículo, Transação e Ordem de Serviço. Cada classe Python vira uma tabela no MySQL — isso se chama ORM, object-relational mapping. A gente escreve em Python, o SQLAlchemy traduz para SQL. Repara em alguns detalhes: o CPF é chave primária de funcionário e cliente, porque é único e natural do domínio. Já o veículo tem o chassi como chave primária — 17 caracteres, único no mundo. Usar chave natural em vez de criar um ID artificial é uma decisão de modelagem importante. Tem também os enums — tipo o cargo, que só aceita três valores: adm, vendedor ou oficina. Se alguém tentar cadastrar "gerente", o banco rejeita. E tem as foreign keys: uma transação aponta para um cliente, um veículo e um vendedor. Isso garante que os dados sempre façam sentido — não tem como registrar uma venda para um cliente que não existe.
👉

⚠️

Slide 13
schemas.py — contratos de dados
⏱ 50 segundos 🎯 Explicar validação
O schemas.py define o formato dos dados. Cada endpoint da API tem um contrato: o que ele aceita receber e o que ele devolve. Isso é feito com Pydantic, que valida automaticamente. Por exemplo: o chassi precisa ter exatamente 17 caracteres, o e-mail precisa ser válido, a senha precisa ter no mínimo 6 caracteres. Se o cliente mandar errado, o FastAPI devolve HTTP 422 antes da rota até executar. A gente tem quatro versões para cada entidade: Base, com os campos comuns; Create, para o POST; Update, com todos os campos opcionais; e Out, que é o formato de resposta. Repara que o Out de funcionário não tem o campo senha_hash — a senha nunca sai do servidor, nem em resposta de API.
👉
Se perguntarem sobre "por que 4 versões?": "Porque cada contexto tem necessidades diferentes. Ao criar, a senha é obrigatória. Ao atualizar, todos os campos são opcionais — você pode querer mudar só o telefone. E na resposta, você nunca quer expor o hash da senha."
💡
Frase pra impactar: "Os schemas alimentam a documentação automática em /docs. A gente não precisa escrever documentação da API manualmente — o FastAPI gera sozinho a partir dos schemas."
Slide 14
auth.py — segurança e JWT
⏱ 70 segundos 🎯 Explicar autenticação
Esse é um dos arquivos mais importantes. Ele cuida da segurança. Tem duas partes: hash de senha e geração de token. Primeiro, senhas. A gente nunca guarda a senha em texto puro. Usamos bcrypt, que é um algoritmo lento de propósito — isso dificulta ataques de força bruta. Cada hash tem um salt aleatório, então a mesma senha gera hashes diferentes. Segundo, o token JWT. Imagina um crachá de balada: você mostra o RG uma vez no login, recebe um crachá, e depois só mostra o crachá — não precisa mostrar o RG de novo. O JWT é esse crachá digital. Ele tem três partes: header, payload e assinatura. No payload vai o CPF do usuário e o cargo. E a assinatura é feita com uma chave secreta que só o servidor tem. Se alguém tentar falsificar o crachá mudando o cargo de vendedor para adm, a assinatura não bate e o servidor rejeita na hora. A função get_current_user faz esse trabalho: ela decodifica o token, valida a assinatura, checa se não expirou, busca o usuário no banco e devolve o objeto pronto para uso. Se qualquer coisa falhar, retorna 401 — não autenticado.
👉
Essa é a fala que a banca vai lembrar. Use a analogia do crachá de balada. Se você só decorar uma analogia da apresentação toda, decore essa.
⚠️
Se a banca te interromper com "mas e se alguém roubar o token?": "É por isso que usamos HTTPS e o token expira em 8 horas. E o payload do JWT não tem senha, só CPF e cargo. Mesmo se alguém interceptar, não consegue fazer nada além de usar por pouco tempo."
💡
Detalhe técnico para impressionar: "O JWT é stateless — o servidor não precisa guardar quem está logado. Isso permite escalar horizontalmente: com 1 servidor ou 100, qualquer um valida o mesmo token só usando a chave secreta."
Slide 15
dependencies.py — autorização
⏱ 40 segundos 🎯 Explicar RBAC
O auth.py responde "quem é você?". O dependencies.py responde "você pode fazer isso?". Tem três funções: require_adm, require_vendedor e require_oficina. Cada uma chama o get_current_user para saber quem é o usuário, e depois checa se o cargo dele bate com o que a rota exige. Se não bate, retorna 403 — proibido. Repara que ADM sempre passa em tudo, porque é superusuário. É tipo o gerente da loja — ele pode fazer qualquer coisa que os outros fazem. Aqui está uma distinção importante: 401 e 403 são coisas diferentes. 401 significa "não sei quem você é" — token inválido. 403 significa "sei quem você é, mas você não pode fazer isso" — falta permissão.
👉
Mostre a cascata: require_adm chama get_current_user, que chama jwt.decode, que chama query no banco. Se qualquer passo falha, para ali.
💡
Frase-chave: "Autenticação é saber quem é. Autorização é saber se pode." Essa frase resume a diferença e impressiona.
Slide 16
routers/ — os endpoints da API
⏱ 45 segundos 🎯 Explicar organização
Os routers são onde as rotas da API são definidas. Cada arquivo cuida de uma área: auth_router cuida do login, funcionarios cuida do CRUD de funcionários, veiculos de veículos, clientes de clientes, transacoes de vendas e devoluções, e ordens_servico das ordens da oficina. Todos seguem o mesmo padrão: um prefixo — tipo /veiculos — uma tag para agrupar no Swagger, e as dependências de segurança em cada rota. Se você olhar a rota de criar funcionário, ela tem Depends(require_adm). Isso significa que só passa quem for ADM. A proteção é aplicada por rota, de forma explícita — não dá para esquecer.
👉
Se perguntarem sobre "por que separar em arquivos?": "Um router por domínio é o padrão de arquitetura limpa. Se eu tiver um bug em veículos, sei exatamente onde olhar. Se amanhã eu quiser adicionar um módulo de peças, crio um arquivo novo e pronto."
Slide 17
API REST — todos os endpoints
⏱ 60 segundos 🎯 Mostrar completude
Aqui está a API completa. Temos 21 endpoints no total, divididos em 6 grupos. Tudo segue o padrão REST: GET para listar, POST para criar, PUT para atualizar, DELETE para excluir. Repara que cada endpoint tem uma indicação de quem pode acessar. Por exemplo, /veiculos no GET qualquer usuário logado pode chamar — porque vendedor e mecânico precisam consultar o estoque. Mas o POST e o DELETE só ADM pode. Também tem endpoints especiais: /transacoes/minhas, que devolve só as vendas do vendedor logado; e /ordens-servico/minhas, que devolve só as OS do mecânico logado. Isso é importante porque garante que cada um vê só o que é seu. E tem os códigos HTTP. 200 é sucesso, 201 é criado, 204 é excluído com sucesso, 400 é regra de negócio violada, 401 é não autenticado, 403 é sem permissão, 404 é não encontrado, 422 é dado inválido.

Slide 18
Regra de negócio — a venda
⏱ 60 segundos 🎯 Mostrar lógica real
Quero destacar uma das regras mais importantes: como uma venda funciona por dentro. Quando o vendedor clica em "realizar venda", acontece o seguinte: Primeiro, o sistema verifica se o cliente existe. Depois verifica se o veículo existe. Depois — e isso é crucial — verifica se o veículo está disponível. Se já estiver vendido, retorna erro 400. Se passou tudo, cria a transação. E repara: o vendedor responsável é pego do token JWT, não vem do frontend. Isso é segurança — o vendedor não consegue fingir ser outro. Depois vem a parte mais importante: o sistema muda a situação do veículo para "vendido" automaticamente. Isso garante que o mesmo veículo não pode ser vendido duas vezes. E tudo isso acontece dentro de uma única transação SQL. Ou tudo funciona, ou nada funciona. Não dá para vender e depois dar erro na hora de marcar como vendido — ou os dois acontecem, ou nenhum.
👉
Pausa dramática no "não vem do frontend". Isso é o tipo de detalhe de segurança que a banca adora. Mostra que você pensou em como evitar fraude.
💡
Termo técnico: isso se chama atomicidade — ou tudo, ou nada. É uma das propriedades ACID dos bancos relacionais. Você pode mencionar para mostrar que sabe.

Preparação
Perguntas que a banca pode fazer
🎯 Decore as 5 principais

Se você decorar só 5 respostas, decore essas:

1. O que é JWT e por que vocês usaram?

JWT é um crachá digital que o servidor dá ao usuário depois do login. Ele contém o CPF e o cargo do usuário, assinado com uma chave secreta que só o servidor tem. Usamos porque é stateless — o servidor não precisa guardar quem está logado. Cada requisição o usuário manda o token e o servidor valida na hora. E se alguém tentar alterar o cargo no token, a assinatura não bate e o servidor rejeita.

2. Como vocês garantem que o usuário só acessa o que pode?

Duas camadas. A primeira é a autenticação: a função get_current_user valida o token JWT em toda requisição. A segunda é a autorização: as dependências require_adm, require_vendedor e require_oficina checam o cargo do usuário antes de cada rota executar. Se o cargo não bate, retorna 403. Além disso, no frontend o menu muda conforme o cargo — mas a segurança de verdade está no backend.

3. Por que CPF como chave primária?

Porque é o identificador natural do domínio. É único por lei, estável, e todo mundo no sistema conhece. Não precisa criar um ID artificial. Já para veículos usamos chassi, que também é único no mundo — 17 caracteres. E para transações e ordens de serviço usamos ID auto-incremento, porque são eventos que podem ter vários por cliente.

4. Por que FastAPI e não Flask ou Django?

FastAPI tem três vantagens: primeira, validação automática com Pydantic — se o cliente manda dados errados, o FastAPI rejeita antes de chegar na rota. Segunda, documentação automática: o Swagger em /docs é gerado sozinho a partir dos schemas. Terceira, performance — é um dos frameworks Python mais rápidos, por causa do suporte nativo a async. Flask exigiria mais código manual; Django é mais pesado e opinativo.

5. O que acontece se dois vendedores tentarem vender o mesmo veículo?

O backend valida antes. Na função de venda, antes de criar a transação, ele checa se a situacao do veículo é "disponivel". Se já foi vendido, retorna erro 400. Como o commit no banco é atômico, não tem como dar corrida — se o primeiro vendedor já mudou o status para "vendido", o segundo recebe erro na hora.
